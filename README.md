# Generation service

Сервис принимает заказ на генерацию, списывает токены, отправляет задачу провайдеру и при отказе идёт к следующей «ноге». Если отказали все ноги, токены возвращаются. Каждое движение денег происходит ровно один раз, даже при дублях вебхуков, гонках между процессами и падениях.

Стек: Python 3.12, FastAPI, PostgreSQL 16, asyncpg (сырой SQL), Alembic, httpx. Сервис работает в 4 процесса (`uvicorn --workers 4`) и не держит состояние в памяти: всё, что нужно для продолжения работы, лежит в базе.

## Запуск

```bash
docker compose up --build
```

Поднимутся:

| Сервис | Адрес с хоста | Что это |
| --- | --- | --- |
| `db` | `localhost:5433` | PostgreSQL (`gen` / `gen`, база `gen`) |
| `migrate` | — | одноразовый контейнер, `alembic upgrade head` |
| `api` | `http://localhost:8000` | сервис, 4 воркера; Swagger на `/docs` |
| `alpha` | `http://localhost:9001` | фейковый провайдер |
| `beta` | `http://localhost:9002` | фейковый провайдер |

`api` стартует только после успешных миграций и здоровых провайдеров.

Пример сценария:

```bash
python - <<'EOF'
import hashlib, hmac, json, urllib.request
body = json.dumps({"payment_id": "p1", "user_id": 1, "tokens": 100, "status": "succeeded"}).encode()
sig = hmac.new(b"dev-secret", body, hashlib.sha256).hexdigest()
req = urllib.request.Request("http://localhost:8000/webhooks/payments", body,
                             {"Content-Type": "application/json", "X-Signature": sig})
print(urllib.request.urlopen(req).read())
EOF

curl -X POST localhost:8000/generate -H 'Content-Type: application/json' \
  -d '{"user_id": 1, "model_slug": "image-fast", "prompt": "a cat", "ref_images": []}'

curl localhost:8000/tasks/<task_id>
curl localhost:8000/users/1/balance
```


Прогон занимает около 1.5 минут: тест позднего `completed` честно ждёт `PROVIDER_TIMEOUT = 60` секунд. Оба его сценария идут параллельно, поэтому ожидание одно.

| Тест | Что проверяет |
| --- | --- |
| `test_payments.py::test_concurrent_identical_payment_webhooks_credit_once` | 20 одновременных одинаковых вебхуков оплаты → одно начисление |
| `test_refund.py::test_concurrent_failures_on_last_leg_refund_once` | 10 одновременных `failed` на последней ноге → один возврат |
| `test_fallback.py::test_first_leg_failure_completes_on_second_leg` | отказ первой ноги → задача завершается на второй, в истории две попытки |
| `test_late_completed.py::test_late_completed_after_watchdog` | поздний `completed` после сторожа: оба случая правила 6 |

Каждый тест создаёт своего пользователя и свой сценарий провайдера (по уникальному промпту), поэтому тесты не мешают друг другу и могут идти на уже работающем стеке.

## Миграции

Схема создаётся только миграциями Alembic (`migrations/versions`). Миграции написаны сырым SQL: список `UPGRADE` и `DOWNGRADE`, каждая строка — один оператор (asyncpg не выполняет несколько операторов в одном prepared statement).

- `0001_schema` — таблицы, индексы, триггеры журнала;
- `0002_catalog` — стартовый каталог моделей и ног.

Применить:

```bash
docker compose run --rm migrate
```

или с хоста: `alembic upgrade head` (берёт `DATABASE_URL` из окружения или `.env`, пример в `.env.example`).

Добавить следующую:

```bash
alembic revision -m "add something" --rev-id 0003
```

Alembic создаст `migrations/versions/0003_add_something.py` из шаблона `migrations/script.py.mako` с уже проставленным `down_revision = "0002"`. Остаётся заполнить `UPGRADE` / `DOWNGRADE` и применить командой выше. Откат: `alembic downgrade -1`.

## Модель данных

- `users` — баланс. Изменить его можно только через журнал (см. ниже).
- `ledger` — журнал операций, только добавление: `payment` (+), `charge` (−), `refund` (+).
- `payments` — последний известный статус каждой оплаты.
- `models`, `legs` — каталог.
- `tasks` — задача: статус `processing | completed | failed`, цена, текущая попытка, результат.
- `attempts` — история попыток: провайдер, приоритет, статус `sending | waiting | completed | failed | timed_out | cancelled`, тип ошибки, `external_id`, дедлайн, флаг `late`.

## Баланс всегда равен сумме журнала

Это гарантирует сама база, а не дисциплина в коде:

- триггер `ledger_apply` на `INSERT` в `ledger` меняет `users.balance` в той же транзакции;
- триггер `users_balance_guard` запрещает менять `balance` откуда-либо, кроме триггера журнала (`pg_trigger_depth()`), и создавать пользователя с ненулевым балансом;
- триггер `ledger_append_only` запрещает `UPDATE` и `DELETE` журнала;
- `CHECK (balance >= 0)` и `CHECK` на знак суммы для каждого вида операции.

Поэтому операции без строки в журнале физически невозможны, а `balance = SUM(ledger.amount)` выполняется всегда. Тесты дополнительно сверяют это после каждого сценария.

## Почему «ровно один раз»

Главный механизм — уникальные индексы в журнале:

- `ledger_one_credit_per_payment (payment_id) WHERE kind = 'payment'` — одна оплата даёт максимум одно начисление;
- `ledger_one_entry_per_task_kind (task_id, kind)` — у задачи максимум одно списание и один возврат.

Вставка идёт через `INSERT ... ON CONFLICT DO NOTHING RETURNING id`: проигравший гонку получает пустой результат и ничего не меняет. Это работает при любом числе процессов и одновременных запросов, потому что решение принимает уникальный индекс в PostgreSQL, а не проверка «а было ли уже» в коде.

**Начисление.** Вебхук оплаты в одной транзакции создаёт пользователя (если его нет), делает upsert в `payments` и, если статус `succeeded`, вставляет строку журнала. 20 одновременных одинаковых вебхуков выстраиваются на уникальном ключе, одна транзакция вставляет строку, остальные 19 получают конфликт и отвечают `credited: false`. Статус `succeeded` в `payments` не перезаписывается более поздним `pending`. Если тот же `payment_id` пришёл с другим пользователем или суммой — 409.

**Списание.** `POST /generate` блокирует строку пользователя (`SELECT ... FOR UPDATE`), проверяет баланс (402) и число активных задач (429), создаёт задачу, строку `charge` и первую попытку — всё одной транзакцией. Блокировка пользователя нужна, чтобы два параллельных запроса не прошли проверку лимита «3 активные задачи» одновременно. Подходящая нога ищется до транзакции: если её нет, 400 возвращается до любых денежных операций.

**Возврат.** Все переходы состояния задачи и её попыток происходят под блокировкой строки задачи (`SELECT ... FOR UPDATE`): вебхук провайдера, синхронная ошибка отправки, сторож. Внутри блокировки код смотрит на статус попытки: если она уже закрыта, событие — дубль, ответ `ignored`. 10 одновременных `failed` на последней ноге: первый закрывает попытку, переводит задачу в `failed` и пишет `refund`; остальные девять ждут блокировку, видят закрытую попытку и ничего не делают. Даже если бы логика статусов где-то ошиблась, второй `refund` упрётся в уникальный индекс.

Блокировка всегда берётся в одном порядке — сначала задача, потом её попытки, — поэтому взаимных блокировок между вебхуками, отправкой и сторожем нет.

## Жизненный цикл задачи

1. `POST /generate` → списание, задача `processing`, попытка `sending` с дедлайном `now() + PROVIDER_TIMEOUT`. Ответ `202 {"task_id"}` уходит сразу, отправка провайдеру идёт фоном после коммита.
2. Отправка: `POST /tasks` провайдеру с `reference` = id попытки и `callback_url`. На `202` попытка становится `waiting` и получает `external_id`. Таймаут, ошибка соединения или не-202 — синхронный отказ (правило 3): попытка `timed_out` / `failed`, задача идёт к следующей ноге.
3. Вебхук провайдера ищет попытку по `reference` или `external_id`. Поиск по `reference` важен: результат может прийти раньше, чем мы записали `external_id`, или вообще после того, как мы не дождались ответа на `POST /tasks`.
4. `completed` → задача `completed`. `failed`:
   - `payload` → задача сразу `failed` + возврат;
   - `technical` → следующая нога;
   - `moderation` → следующая нога, но ноги с `skip_on_moderation` пропускаются.
5. Ноги кончились → задача `failed` + один возврат.

Следующая нога — нога той же модели с большим приоритетом, принимающая столько же референсов. `skip_on_moderation` трактуется так: если в истории задачи уже был отказ по модерации, такие ноги пропускаются. Проверяется вся история, а не только последняя попытка: контент, который один провайдер отверг по модерации, не стоит отправлять ноге, которая просила его не присылать, даже если между ними был технический сбой.

## Сторож и несколько процессов

Сторож запускается в каждом из 4 процессов и раз в `WATCHDOG_INTERVAL` секунд ищет открытые попытки с истёкшим дедлайном:

```sql
SELECT a.id, a.task_id FROM attempts a JOIN tasks t ON t.id = a.task_id
WHERE a.status IN ('sending', 'waiting') AND a.deadline_at < now()
ORDER BY a.deadline_at LIMIT 1
FOR UPDATE OF t SKIP LOCKED
```

`SKIP LOCKED` распределяет работу: задачу, которую уже обрабатывает другой процесс (сторож или вебхук), остальные пропускают и берут следующую. Под блокировкой статус попытки перепроверяется, так что даже при неудачном совпадении работа не задваивается. Просроченная попытка становится `timed_out` и дальше идёт по тем же правилам, что и отказ `technical`: следующая нога или возврат. Лидер-выборы и advisory-локи не нужны.

## Что будет при падении процесса посреди обработки вебхука

Обработка вебхука — одна транзакция: закрыть попытку, перевести задачу, записать возврат или открыть следующую попытку. Отправка следующей попытки провайдеру идёт только после коммита.

- **Упал до коммита.** PostgreSQL откатывает транзакцию, как будто вебхука не было. Провайдер не получил 2xx и повторит доставку (реальные провайдеры так делают); повтор будет обработан с нуля. Если повтора не будет, попытка останется открытой, и её закроет сторож по дедлайну — задача не зависнет.
- **Упал после коммита, до ответа провайдеру.** Состояние уже записано. Повтор вебхука придёт в закрытую попытку и получит `ignored`. Деньги не двигаются второй раз.
- **Упал после коммита, до отправки следующей ноги.** Новая попытка лежит в базе в статусе `sending` с дедлайном. Никакой процесс её не отправит, но через `PROVIDER_TIMEOUT` сторож посчитает её неудачной и поведёт задачу дальше: к следующей ноге или к возврату. Задача не теряется и не зависает, а деньги не теряются. Цена такого решения — эта нога фактически не была опробована. Альтернатива — повторная отправка «застрявших» `sending`, но она требует идемпотентности на стороне провайдера по `reference`; для тестового это сознательно не сделано.
- **Упал во время `POST /tasks` к провайдеру.** То же самое: попытка `sending`, её закроет сторож. Если провайдер всё-таки принял задачу и пришлёт результат до дедлайна, он будет принят как обычно — поиск идёт по `reference`. Если после дедлайна — это случай правила 6.

## Правило 6: поздний `completed`

Ситуация: сторож признал попытку `timed_out`, а потом от провайдера пришёл `completed`. Задача не должна получить и результат, и возврат. Решение зависит от того, в каком состоянии задача в момент прихода результата (решается под блокировкой задачи, поэтому гонки со сторожем и другими вебхуками нет):

1. **Задача ещё `processing`** (идёт следующая нога, возврата не было). Поздний результат **принимается**: задача становится `completed` с этим результатом, попытка помечается `completed` + `late = true`, текущая открытая попытка — `cancelled`. Её будущий вебхук попадёт в закрытую попытку и будет проигнорирован. Пользователь быстрее получает результат, за который уже заплатил; возврата не было и не будет. Лишнюю работу второго провайдера оплачиваем мы — это расход сервиса, а не пользователя.
2. **Задача уже `failed` и токены возвращены.** Результат **отбрасывается**: задача остаётся `failed`, возврат остаётся. В попытке сохраняется `result_url` и `late = true` — для разбора и поддержки, но наружу результат не отдаётся. Отнимать токены обратно без согласия пользователя (повторное списание) нельзя: баланс мог быть уже потрачен, и это неожиданное движение денег.
3. **Задача уже `completed` другой ногой.** Результат отбрасывается так же, денег это не касается.

Поздний `failed` после таймаута просто игнорируется: эта попытка уже засчитана как неудачная.

То же правило работает для синхронного таймаута на `POST /tasks`: мы не дождались ответа, попытка `timed_out`, а провайдер мог задачу принять и позже прислать результат.

## Фейковые провайдеры

Одно приложение `providers/app.py`, запущенное дважды с `PROVIDER_NAME=alpha|beta`. `POST /tasks` отвечает `202 {"external_id"}` и через `delay_min..delay_max` секунд (по умолчанию 2–20) шлёт подписанный вебхук на `callback_url`.

Поведение:

| Поле | Что делает |
| --- | --- |
| `failure_rate`, `failure_type` | доля отказов и их тип: `technical`, `moderation`, `payload` |
| `sync_failure_rate`, `sync_failure`, `hang_seconds` | синхронный отказ на `POST /tasks`: `503` или зависание на `hang_seconds` (таймаут у клиента) |
| `duplicate_rate` | вебхук отправляется дважды одновременно |
| `drop_rate` | вебхук не отправляется совсем |
| `delay_min`, `delay_max` | задержка вебхука; `> PROVIDER_TIMEOUT` даёт поздний `completed` |

Настройки задаются:

- при старте: `PROVIDER_BEHAVIOR='{"failure_rate": 0.3}'`;
- на лету: `PUT /config` (всё целиком), `PUT /scenarios/{prompt}` (поведение для задач с таким промптом), `DELETE /scenarios/{prompt}`, `GET /config`.

Сценарии по промпту позволяют тестам работать параллельно на одном стеке.

## Подпись вебхуков

`X-Signature` = hex HMAC-SHA256 сырого тела запроса с общим секретом `WEBHOOK_SECRET`. Проверяется до разбора JSON, сравнение через `hmac.compare_digest`. Неверная подпись — 401.

## API

| Запрос | Ответ |
| --- | --- |
| `POST /generate` | `202 {"task_id"}`; 400 — нет подходящей ноги, 402 — мало токенов, 404 — нет модели или пользователя, 429 — 3 активные задачи |
| `POST /webhooks/providers/{name}` | `{"outcome": "completed" | "next_leg" | "failed" | "ignored" | "late_accepted" | "late_discarded"}` |

## Допущения

- Пользователь создаётся первой оплатой: регистрации нет, а без оплаты генерировать всё равно нечем. `POST /generate` для неизвестного пользователя — 404.
- Любой не-202 ответ на `POST /tasks` считается синхронным отказом и ведёт к следующей ноге: мы не знаем, отвергнет ли другой провайдер тот же запрос.
- Ссылка на результат — строка от провайдера, файлы не хранятся.
